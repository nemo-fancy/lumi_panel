### 0.2 术语

| 术语 | 含义 |
|---|---|
| 面板 / Panel | 本项目,控制平面 |
| 机器 / Machine | 一台主机,运行一个 LumiNode 进程 |
| 节点 / Node | 一个逻辑代理入口(协议+端口+参数),一台 Machine 可承载 N 个 |
| 南向 | 面板 ↔ 节点端 |
| 北向 | 面板 ↔ 客户端(订阅) |
| 兼容面 | 为兼容既有生态实现的 V2Board 契约 |
| 原生面 / LNP | 面板与 LumiNode 之间的自研协议(**v1.1**) |

### 0.3 三条贯穿全文的设计原则

```
① 能用数据库约束表达的不变量,一律加约束。
   应用层逻辑会有 bug,约束不会。

② 权威判定绝不依赖定时任务的按时执行。
   到期、配额这类判定必须是计算出来的,不是被 cron 写出来的。

③ 副作用只走事件总线,不在 handler 里逐个调用。
   否则每新增一个管理动作,就会漏掉一路副作用。
```

## 1. 项目定位与目标

### 1.1 竞品结论

| 面板 | 血统 | 栈 | 状态 |
|---|---|---|---|
| V2Board | 始祖 | PHP/Laravel | 2023-06 停更,定义了生态的节点 API 契约 |
| xiaoV2b | V2Board 分支 | PHP/webman | 活跃 |
| Xboard | V2Board 分支 | PHP/Laravel+Octane | **生态主流**,4K+ stars,插件系统 |
| PPanel | 独立重写 | Go + Next.js | UI 最好,需 Node 运行时,生态小 |
| V3Board | 独立重写 | TS/Bun + PG | v1.0 阶段 |

**两个关键事实:**

1. **生态锁**:所有节点后端(XrayR / V2bX / soga / ppanel-node)都按 V2Board 契约实现。这是唯一绕不开的东西。
2. **功能已同质化**:三家的用户端与管理端模块几乎重合。**再堆功能没有意义,差距在运营工具与系统一致性。**

**历史教训**:CVE-2026-39912 —— 魔法登录 token 被直接写进 HTTP 响应体,导致未授权账号接管(含管理员),影响 V2Board 1.6.1~1.7.4 与 Xboard ≤0.1.9。这不是实现 bug,是架构上缺少"认证凭据必须带外传递"这条铁律。本项目在类型系统层面强制(§12.1)。

### 1.2 设计目标

| 优先级 | 目标 | 验收标准 |
|---|---|---|
| P0 | 单二进制部署 | 一个可执行文件 + 一个配置文件,无需 Node/PHP 运行时 |
| P0 | 计费绝对正确且**可自证** | 不变量校验器持续运行,崩溃恢复后误差为 0 |
| P0 | 南向兼容 | 未改动的 XrayR/V2bX/soga 零配置接入 |
| P0 | 高吞吐计量 | 2 vCPU 支撑 200 节点 × 5000 用户,DB 写 QPS < 20 |
| P0 | 前后台状态一致 | 管理动作的全部副作用由事件总线保证,有测试断言 |
| P1 | 运营效率工具 | 用户自助诊断、节点批量轮换、财务对账 |
| P1 | 一键迁移 | 从 Xboard 迁入,用户零感知 |
| P2 | 原生控制面(LNP) | 秒级下线、增量同步 |

### 1.3 明确不做

- 不做微服务。模块化单体是正确形态。
- 不做 MySQL 运行时主库(仅作迁移数据源)。
- 不做通用计费/CRM 平台。
- 不做与 V2Board 的 schema 兼容(只做单向导入)。
- **不做面板内置节点部署(一键开节点)** —— 面板将持有所有 VPS 的 SSH 凭据,面板被攻破 = 全部服务器沦陷。
- **不做签到/积分/抽奖等游戏化** —— 制造无效负载、必被脚本刷。
- 不做自建 IM 客服(Crisp/Tawk/TG 已够用)。
- **子站 / 白标分销留到 v2 单独决策** —— 多租户会渗透到每一张表,不能顺手加。

## 2. 技术选型

### 2.1 后端:Go

**决定性理由:面板与 LumiNode 共享一个 protocol 模块。**

V2bX 是 Go 项目。面板同用 Go,可把契约抽成独立 module,两边同时 import:

- 契约漂移在**编译期**暴露,而不是线上节点静默取到零值 —— 这是 V2Board 生态最常见的故障类型
- 可直接复用 sing-box / xray-core 的 option struct 生成节点配置,而非手拼 JSON
- 单二进制 + 交叉编译 + `embed.FS`

**诚实的边界**:在 v1(LNP 推迟、自研协议可选)的范围内,共享模块的收益尚未完全兑现,v1 的 Go 优势主要来自单二进制、并发模型与生态同语言。**完整收益在 v1.1 到来。**

**否决的候选**:Rust(与 V2bX 无类型共享,Web 后台生态不足,对本项目瓶颈无提升)、TS/Bun(V3Board 已占,单二进制弱)、Kotlin/JVM(内存基线 200MB+ 与"小鸡上跑"冲突)。

> 关于 Kotlin:考虑到 Android 背景,它是舒适区。但本项目的核心难点恰是 JVM 短板。建议 Kotlin 投入放到 Lumi 客户端 Android 端。

### 2.2 依赖选型

| 层 | 选型 | 说明 |
|---|---|---|
| HTTP | `net/http` + `chi` | 不用 Gin(context 抽象在流式与 HTTP/2 下别扭) |
| DB 访问 | `sqlc` | 热路径必须看得见 SQL。**不用 GORM** |
| Schema 迁移 | `atlas` | 声明式 |
| 缓存/热层 | `go-redis/v9` | **硬依赖,非可选** |
| 任务队列 | `asynq` | 邮件、回调重试、报表 |
| 定时 | `gocron` + Redis 锁 | |
| 配置 | `koanf` | 文件+env+DB 三级 |
| 日志 | `log/slog` | |
| 模板/表达式 | `text/template` + `expr-lang/expr` | |
| WASM 插件 | `wazero` | 纯 Go,无 CGO |
| SQLite | `modernc.org/sqlite` | 纯 Go |

**强制约束:全程 `CGO_ENABLED=0`。** 一旦引入 CGO,交叉编译与静态链接就废了。

### 2.3 前端:React + Vite,纯 SPA

**不用 Next.js。** 这是 PPanel 的架构负担 —— SSR/RSC 需要常驻 Node 进程,导致它必须多组件部署,永远无法单二进制。面板登录后全是鉴权数据,SSR 收益接近零。

| Bundle | 路径 | 说明 |
|---|---|---|
| landing | `/` | 构建期静态生成(v1 用简单模板) |
| user | `/app/*` | 用户端 SPA |
| admin | `/{secure_path}/*` | 管理端 SPA,路径随机化 |

### 2.4 数据库

**主库 PostgreSQL 16+;SQLite 供轻量部署;MySQL 仅作迁移数据源。**

选 PG 的硬理由:声明式分区、`INSERT ... ON CONFLICT` 批量 UPSERT、`JSONB`、部分索引。

**不做 MySQL 运行时兼容**:多方言会迫使放弃 sqlc 的类型安全。这个税太贵,而存量用户本来就要做一次迁移。

## 3. 总体架构

```
   客户端    Lumi │ mihomo 系 │ sing-box 系 │ 通用链接列表客户端
                 └──────────┬──────────────┘
                            │ HTTPS 订阅
   ┌────────────────────────▼─────────────────────────┐
   │            北向 · Subscription Plane              │
   │   UA 识别 → 能力过滤 → IR 构建 → Renderer → 输出   │
   ├──────────────────────────────────────────────────┤
   │            业务层 Services                        │
   │  auth │ plan │ order │ pay │ ticket │ invite      │
   │  coupon │ notify │ diagnose │ risk │ finance      │
   ├──────────────────────────────────────────────────┤
   │      ★ 领域事件总线 Event Bus(§9)                │
   │  管理动作的唯一副作用出口 → 扇出到各订阅者          │
   ├──────────────────────────────────────────────────┤
   │            计量核心 Metering Core(§7)            │
   │  Ingest → Accumulator → Quota → Flusher           │
   │  ★ 不变量校验器 Invariant Checker                 │
   ├──────────────────────────────────────────────────┤
   │            南向 · Node Plane                      │
   │  ┌──────────────────┐  ┌────────────────────┐    │
   │  │ Compat(V2Board)  │  │ Native LNP  [v1.1] │    │
   │  └──────────────────┘  └────────────────────┘    │
   └──────┬───────────────────────────┬───────────────┘
          │                           │
   ┌──────▼──────────┐        ┌───────▼─────────────┐
   │ XrayR / V2bX    │        │ LumiNode            │
   │ soga(未改动)     │        │ (V2bX + lumi core)  │
   └─────────────────┘        └─────────────────────┘

   存储   PostgreSQL(状态) │ Redis(热层/队列/锁/事件)
```

### 3.1 模块划分

```
internal/
├── metering/       计量核心 —— 技术护城河
│   ├── ingest.go       上报接收与幂等(seq)
│   ├── accumulator.go  分片累加器
│   ├── ladder.go       Flusher 本地权威配额账本
│   ├── flusher.go      两阶段幂等落库
│   ├── quota.go        配额引擎
│   ├── limiter.go      设备/IP 限制
│   └── invariant.go    ★ 不变量校验器
├── events/         领域事件总线 + 订阅者注册表
├── nodeplane/
│   ├── compat/         V2Board 契约(uniproxy / legacy)
│   ├── native/         LNP  [v1.1]
│   └── registry.go     节点注册、能力协商、健康
├── subplane/
│   ├── detect.go       UA 识别(有序规则)
│   ├── capability.go   协议能力过滤
│   ├── ir.go           中间表示
│   └── render/         base64 / mihomo / singbox
├── domain/         纯逻辑,无 IO
├── store/          sqlc 生成 + repository
├── service/        业务编排
├── api/            handler(user / admin / open)
├── plugin/         三层扩展
├── migrate/        从竞品导入
└── platform/       config / log / metrics / mail / cron / secret
```

**依赖铁律**:`api → service → domain ← store`。`domain` 不 import 任何 IO 包。`metering` 是唯一允许直接触 store/redis 的非 service 包(性能例外,需注释标注)。

### 3.2 进程与角色

```bash
lumipanel serve                # 全角色
lumipanel serve --role=api     # 仅 API(可多副本)
lumipanel serve --role=worker  # 计量 + 定时(★ 必须单实例)
lumipanel migrate up
lumipanel import xboard --dsn=... --dry-run
lumipanel reconcile --dry-run  # 不变量校验与修复
lumipanel doctor
lumipanel rotate-key --old --new
```

> **★ 关键部署约束**:`worker` 角色持有 Flusher 的**内存权威配额账本**(§7.3),**必须单实例**。它用 Redis 分布式锁(带 fencing token)抢占,抢不到则以只读模式启动并告警 —— **不能靠部署纪律保证**。这是 v1 唯一的有状态单点,必须写进部署文档首页。

## 4. 数据模型

### 4.1 相对 V2Board 的改进

| V2Board 的问题 | 本项目 |
|---|---|
| 套餐字段直接挂 users 表,一用户仅一套餐 | 独立 `subscriptions` 表:**1 条 primary + N 条 data_pack** |
| 机器与入口混为一谈 | 拆 `machines` / `nodes` |
| 流量直接 UPDATE users 行 | 追加写 `traffic_ledger` + 异步 rollup |
| 配置存 PHP 文件 | 全部入库 + 加密 + 变更历史 |
| 无审计 | `audit_logs` 全覆盖 |
| 到期靠 cron 写 status | **到期是计算出来的**,cron 只维护缓存 |

### 4.2 订阅模型:1 primary + N data_pack

**这是从"任意 N 条并存"收窄后的结论。** 原设计产生了四个 S1 缺陷与大量归属复杂度,而真实场景只有"主套餐 + 临时流量包"。

```
扣费顺序固定:先 data_pack(按到期时间升序),再 primary
数据库强制:  同一时刻最多一条 active primary
```

收益:归属算法退化为"遍历几条、顺序固定",不需要 priority 字段;绝大多数用户只有一条订阅。

### 4.3 核心表定义(已应用全部修正)

```sql
-- ========== 用户 ==========
CREATE TABLE users (
    id              BIGSERIAL PRIMARY KEY,
    email           CITEXT UNIQUE NOT NULL,
    password_hash   TEXT NOT NULL,              -- argon2id(用户密码用慢哈希)
    uuid            UUID UNIQUE NOT NULL,       -- 代理协议用户标识
    token           TEXT UNIQUE NOT NULL,       -- 订阅 token,可轮换
    is_admin        BOOLEAN NOT NULL DEFAULT FALSE,
    is_staff        BOOLEAN NOT NULL DEFAULT FALSE,
    banned_at       TIMESTAMPTZ,
    balance         BIGINT NOT NULL DEFAULT 0,  -- 最小货币单位,禁止浮点
    commission_rate SMALLINT,
    invite_user_id  BIGINT REFERENCES users(id),
    speed_limit     INTEGER,
    device_limit    SMALLINT,
    remark          TEXT,
    deleted_at      TIMESTAMPTZ,                -- 匿名化而非物理删除
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_users_invite ON users(invite_user_id) WHERE invite_user_id IS NOT NULL;

-- ========== 套餐 ==========
CREATE TABLE plans (
    id              BIGSERIAL PRIMARY KEY,
    name            TEXT NOT NULL,
    -- ★ 只有两种。试用 = 短周期低价的 primary,不单列一类
    kind            TEXT NOT NULL CHECK (kind IN ('primary','data_pack')),
    group_ids       BIGINT[] NOT NULL DEFAULT '{}',
    transfer_bytes  BIGINT NOT NULL,
    speed_limit     INTEGER,
    device_limit    SMALLINT,
    prices          JSONB NOT NULL,             -- {"month":990,"year":9900} 单位:分
    reset_policy    TEXT NOT NULL CHECK (reset_policy IN ('monthly_1st','monthly_signup','never')),
    change_policy   TEXT NOT NULL DEFAULT 'prorate'
                    CHECK (change_policy IN ('reset','prorate','stack','deny')),
    stock           INTEGER,
    is_visible      BOOLEAN NOT NULL DEFAULT TRUE,
    is_renewable    BOOLEAN NOT NULL DEFAULT TRUE,
    audience        JSONB NOT NULL DEFAULT '{}',-- 受众条件(权限组/注册时长等)
    sort            INTEGER NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ========== 订阅 ==========
CREATE TABLE subscriptions (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    plan_id         BIGINT NOT NULL REFERENCES plans(id),
    kind            TEXT NOT NULL CHECK (kind IN ('primary','data_pack')),
    status          TEXT NOT NULL CHECK (status IN ('active','expired','suspended')),
    transfer_bytes  BIGINT NOT NULL,
    used_bytes      BIGINT NOT NULL DEFAULT 0,  -- rollup 结果,非实时权威
    reset_epoch     INT NOT NULL DEFAULT 0,     -- 重置代次,防在途 flush 错算
    started_at      TIMESTAMPTZ NOT NULL,
    expired_at      TIMESTAMPTZ,                -- NULL = 永久(流量包)
    last_reset_at   TIMESTAMPTZ,
    next_reset_at   TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- ★ 数据库强制:同一时刻最多一条 active primary
CREATE UNIQUE INDEX uq_sub_one_primary ON subscriptions(user_id)
    WHERE kind = 'primary' AND status = 'active';
CREATE INDEX idx_sub_user_active ON subscriptions(user_id) WHERE status = 'active';
CREATE INDEX idx_sub_expiring ON subscriptions(expired_at) WHERE status = 'active';

-- ========== 机器与节点 ==========
CREATE TABLE machines (
    id              BIGSERIAL PRIMARY KEY,
    name            TEXT NOT NULL,
    -- ★ SHA-256 而非 argon2:api_key 是 32 字节高熵随机串,
    --   慢哈希无安全收益,却让重连风暴变成自我 DoS
    api_key_hash    TEXT NOT NULL,
    agent_version   TEXT,
    upstream_base   TEXT,                       -- fork 基线版本,便于排查
    capabilities    JSONB NOT NULL DEFAULT '{}',-- 能力协商结果
    monthly_cost    BIGINT,                     -- 成本录入,供财务视图
    last_seen_at    TIMESTAMPTZ,
    online          BOOLEAN NOT NULL DEFAULT FALSE,
    load_avg        REAL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE nodes (
    id              BIGSERIAL PRIMARY KEY,
    machine_id      BIGINT REFERENCES machines(id) ON DELETE SET NULL,
    name            TEXT NOT NULL,
    protocol        TEXT NOT NULL,
    host            TEXT NOT NULL,              -- 对客户端暴露
    port            INTEGER NOT NULL,
    server_port     INTEGER,                    -- 节点实际监听(中转场景不同)
    group_ids       BIGINT[] NOT NULL DEFAULT '{}',
    -- ★ 整数基点:100 = 1.00x。浮点会导致同样流量分批不同算出不同结果
    rate_bp         SMALLINT NOT NULL DEFAULT 100,
    settings        JSONB NOT NULL DEFAULT '{}',
    parent_id       BIGINT REFERENCES nodes(id),-- 单级中转:入口 → 落地
    visible_to      TEXT NOT NULL DEFAULT 'all' CHECK (visible_to IN ('all','lumi_only')),
    tags            TEXT[] NOT NULL DEFAULT '{}',
    health_status   TEXT NOT NULL DEFAULT 'unknown',
    is_visible      BOOLEAN NOT NULL DEFAULT TRUE,
    sort            INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_nodes_groups ON nodes USING GIN(group_ids);
-- ★ 同机端口唯一,避免等到节点起不来才发现冲突
CREATE UNIQUE INDEX uq_node_machine_port ON nodes(machine_id, server_port)
    WHERE machine_id IS NOT NULL AND server_port IS NOT NULL;

-- ========== 流量账本 ==========
-- ★ subscription_id NOT NULL DEFAULT 0:
--   PostgreSQL 中唯一索引里的 NULL 彼此不相等,可空会让唯一约束形同虚设,
--   ON CONFLICT 永不触发 → 无限膨胀 + 重复计费
CREATE TABLE traffic_ledger (
    user_id         BIGINT NOT NULL,
    node_id         BIGINT NOT NULL,
    subscription_id BIGINT NOT NULL DEFAULT 0,  -- 0 = 超额溢出,无归属
    up_bytes        BIGINT NOT NULL,
    down_bytes      BIGINT NOT NULL,
    billed_bytes    BIGINT NOT NULL,
    rate_bp_snapshot SMALLINT NOT NULL,         -- 快照倍率,供历史复算
    bucket_at       TIMESTAMPTZ NOT NULL,       -- 面板接收时刻,归整 5 分钟 —— 用于计费与幂等
    origin_at       TIMESTAMPTZ NOT NULL        -- 节点声称的窗口 —— 用于图表
) PARTITION BY RANGE (bucket_at);
CREATE UNIQUE INDEX uq_ledger ON traffic_ledger(user_id, node_id, subscription_id, bucket_at);

-- ★ 幂等闸门:加法 UPSERT 不幂等,WAL 回放会重复计费
CREATE TABLE traffic_batches (
    batch_id    UUID PRIMARY KEY,
    flushed_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ★ node_id 用 0 哨兵表示"全部节点合计":
--   PRIMARY KEY 列隐式 NOT NULL,不能靠 NULL 表达聚合行
CREATE TABLE traffic_daily (
    user_id      BIGINT NOT NULL,
    day          DATE   NOT NULL,
    node_id      BIGINT NOT NULL DEFAULT 0,
    billed_bytes BIGINT NOT NULL,
    PRIMARY KEY (user_id, day, node_id)
);
```

**其余表**(`orders` / `payments` / `coupons` / `tickets` / `ticket_messages` / `invite_commissions` / `balance_logs` / `devices` / `settings` / `settings_history` / `node_configs` / `audit_logs` / `notices` / `knowledge` / `email_suppressions` / `unknown_clients`)遵循同样约定:

- **所有金额用 `BIGINT` 存最小货币单位**,禁止 `FLOAT`/`DECIMAL`
- **所有时间用 `TIMESTAMPTZ`**,应用层统一 UTC
- **软删除用 `deleted_at`** 而非 `is_deleted`
- **动态字段用 `JSONB` + 应用层 schema 校验**,不加宽表
- **所有余额变动必须同时写 `balance_logs`**(前后值 + 业务单号),供对账

### 4.4 容量与保留

```
5000 活跃用户 × 3 节点 × 5 分钟粒度
  ≈ 4.32M 行/天 ≈ 260 MB/天 ≈ 7.8 GB/月
```

- `traffic_ledger` 只保留 **35 天**,超期分区 `DETACH` 后归档
- 长期统计只留 `traffic_daily`(约 15 万行/月)
- 定时任务提前 7 天建下月分区
- **这个策略必须在 v1 就实现**,否则三个月后磁盘爆掉

### 4.5 迁移安全(expand-contract 强制)

给数亿行的分区表加 `NOT NULL` 列会长时间持 `ACCESS EXCLUSIVE` 锁,面板全站卡死。

```
禁止:ADD COLUMN ... NOT NULL(无默认值/大表)
禁止:ALTER COLUMN TYPE(重写整表)
禁止:大表上直接 CREATE INDEX(必须 CONCURRENTLY)
禁止:迁移脚本中的长事务
要求:加列三步 —— 加可空列 → 双写回填 → 加约束
      迁移标注预估锁时长,超 1s 需显式 --allow-lock
CI:  在千万行种子库上跑迁移,断言锁时长
```

## 5. 南向:节点接口

### 5.1 双栈,v1 只做兼容面

```
Compat Plane(v1)   HTTP/JSON,轮询    给 XrayR / V2bX / soga / LumiNode
Native LNP(v1.1)   gRPC 双向流        给 LumiNode
```

**为什么 LNP 推迟**:它是整个项目最复杂的子系统(跨副本会话路由、节点配额镜像、流背压、灰度回滚),而换来的只是"超额下线从 60 秒变成 1 秒"。粗算该延迟造成的损失约每天 10GB,远低于开发与运维风险。

**关键:这不影响 LumiNode 与自研协议。** 自研协议参数完全可以通过兼容面的 `config` 端点用扩展字段下发 —— V2Board 契约里节点配置本来就是自由结构。

**代价(需接受)**:超额下线延迟 ≤60s;配置下发等一个轮询周期;兼容面不提供 at-least-once 保证。

### 5.2 兼容面契约

**新版(V2Board 1.7.0+,必须实现)**

| 端点 | 方法 | 用途 |
|---|---|---|
| `/api/v1/server/UniProxy/config` | GET | 拉取节点配置 |
| `/api/v1/server/UniProxy/user` | GET | 拉取授权用户 |
| `/api/v1/server/UniProxy/push` | POST | 上报流量 |
| `/api/v1/server/UniProxy/alive` | POST | 上报在线 IP |

参数:`token`、`node_id`、`node_type`。

**必须复刻的生态怪癖**:`vless` 不是独立的 `node_type` —— XrayR 通过 `EnableVless` 开关把 `node_type=v2ray` 解释成 vless。不复刻,老节点接不上。

**实现要点**

- `config` 带 `ETag`,节点携 `If-None-Match`,未变返回 304
- `user` 带 `users_hash`(覆盖用户集 + uuid + 限速),节点比对后决定是否重建
- `push` **必须幂等**:按 `(node_id, seq)` 去重;老客户端不带 seq 时退化为时间窗去重
- 错误响应保持 `{"status":"fail","message":"..."}` 形状,否则 XrayR 会 panic 而非重试

**旧版(1.7.0 前)**:`Deepbwork` / `Tidalab` 系列。**默认关闭**,管理员显式开启,UI 标注"仅迁移期使用"。

### 5.3 上报语义(契约的关键条款)

这是节点端与面板之间最容易理解错的一点,理解错就是 100% 计费错误。写进 protobuf 注释与契约测试:

```
语义:  增量(delta since last successful report),不是累计
传输:  at-least-once
节点:  必须在收到面板 ACK 之后才清空本地计数器
       未 ACK 则累积到下次上报,并复用同一 seq
ACK:   含义是"已进入 Accumulator + WAL",不是"已落库"

兼容面的固有弱点(需在文档中声明):
  XrayR/V2bX 收到任意 2xx 就清零。若面板返回 2xx 后、WAL 之前崩溃,
  这段流量永久丢失。这是选择兼容旧生态的代价。
```

### 5.4 能力协商

节点在 `config` 拉取时上报:

```json
{
  "agent": {"name":"LumiNode","version":"1.2.0","upstream_base":"V2bX-vX.Y.Z"},
  "cores": ["xray","sing","lumi"],
  "protocols": ["vmess","vless","trojan","shadowsocks","hysteria2","tuic","anytls","lumi"],
  "features": ["reality","xtls-vision","multiplex"]
}
```

**三层防护**(针对"节点静默跳过不支持的协议"这类无报错故障):

1. 面板**拒绝**把节点不支持的协议分配给它(下发前拦截)
2. 节点 inbound 启动失败**必须上报**,不得静默跳过
3. 面板收到失败上报 → 自动从订阅摘除 + 后台红标 + 告警

兼容面节点不上报能力 → 按最保守集合处理,后台标注"能力未知"。

### 5.5 权限缓存

**按权限组缓存,不按节点。** 5000 用户 × 200 节点 = 100 万 SET 成员,且任何订阅变更要遍历所有节点。

```
group:users:{group_id} → SET of user_id
node → group_ids 静态配置,节点侧取并集
失效:订阅变更时只更新受影响的 1~2 个组
```

### 5.6 配置灰度下发

即使在轮询模型下,一次错误配置也能让全网同时故障。

```
分批:  5% → 25% → 100%,每批间隔 60s
门禁:  每批后检查心跳与 NodeStatus,失败率 >20% → 停止并回滚
版本:  node_configs 保留最近 10 版,一键回滚
预览:  管理端"生效配置 diff"按钮
```

## 6. 北向:订阅与客户端适配

### 6.1 两个正交维度(最重要的澄清)

```
维度一 · 格式    输出成 YAML / JSON / base64
维度二 · 协议能力 该客户端能否解析 hy2 / tuic / anytls / reality
```

**砍掉维度一,不等于可以砍掉维度二。** 老 Clash Premium 不认识 hy2/tuic/anytls,不做能力过滤就直接下发:好的客户端跳过未知项(用户看到"节点少了一半"),差的整个解析失败(**节点列表为空**)。

而"没节点"恰恰是客服最无法自助排查的一类工单。**因此 UA 识别层无论如何都必须存在,它同时承担能力过滤。**

### 6.2 渲染管线

```
HTTP 请求
   ↓ 1. Detect      UA / ?target= / ?flag= → ClientProfile
   ↓ 2. Capability  按 Profile 过滤掉不支持的协议节点
   ↓ 3. Build IR    订阅 + 权限组 + 节点集 → 中间表示(过滤/排序/改名/倍率标注)
   ↓ 4. Render      IR + 模板 → 目标格式
响应(含流量头 / 到期头 / 缓存头)
```

**IR 层是必需的**:否则每加一个客户端就要重写一遍过滤、排序、倍率、权限逻辑 —— 这正是 V2Board 系订阅代码难以维护的根因。

### 6.3 v1 渲染器:三个

| 渲染器 | 覆盖客户端 | 累计用户覆盖 | 估时 |
|---|---|---|---|
| base64 链接列表 | v2rayN/NG、NekoBox、Throne、**Shadowrocket**(其原生格式) | ~55% | 3 天 |
| mihomo YAML | Clash Verge Rev、ClashX Pro、CFA、FlClash、OpenClash、Stash | ~90% | 1 周 |
| sing-box JSON | SFA/SFI/SFM、Hiddify、Karing | ~97% | 1 周 |

**为什么是 3 而不是 1**:成本曲线强非线性 —— 前三个 2.5 周覆盖 97%,后四个(Surge/QX/Loon/Egern)再花 2.5 周只多覆盖 3%。而只出一种时三个候选都会打穿一大块用户:只出 mihomo 则 iOS 的 Shadowrocket 用户失效;只出 base64 则全体桌面用户失去规则分流(这不是客服能解答的问题,是产品能力缺失);只出 sing-box 则最大的 Clash 家族全废。

**为什么不是 12**:长尾客户端用户是能自行转换的高级用户。**客服组承接最后 3%,不是前 40%。**

### 6.4 UA 识别:有序规则,不是 map

Go 的 map 迭代顺序是随机的。`"Clash Verge Rev"` 同时匹配 `clash` 与 `clash-verge`,用 map 会导致同一用户刷新订阅时随机拿到不同格式 —— 这类非确定性 bug 会消耗大量客服时间。

```go
// 有序切片,最具体在前,首个命中即返回
var uaRules = []uaRule{
    {contains: []string{"clash-verge","clash.meta","mihomo","flclash","nikki"}, profile: Mihomo},
    {contains: []string{"sing-box","sfa","sfi","sfm","hiddify","karing"},        profile: SingBox},
    {contains: []string{"stash"},   profile: Mihomo},        // 必须早于 clash
    {contains: []string{"clash"},   profile: ClashPremium},  // 兜底
    {contains: []string{"shadowrocket","v2rayn","v2rayng","nekobox","throne"}, profile: Base64},
}
// 未命中 → 记入 unknown_clients 表(见 §9.4)+ 返回 base64
```

优先级:`?target=` > `?flag=` > UA > 用户后台设置 > 全局兜底(base64)。

配套 **golden test**:60+ 条真实 UA fixture,任何规则改动跑全量断言。这个 fixture 是资产,持续积累。

### 6.5 协议能力矩阵

| 协议 | mihomo | sing-box | Clash Premium | Shadowrocket | v2rayN/NG |
|---|:---:|:---:|:---:|:---:|:---:|
| SS / VMess / Trojan | ✅ | ✅ | ✅ | ✅ | ✅ |
| VLESS(含 Reality) | ✅ | ✅ | ❌ | ✅ | ✅ |
| Hysteria2 | ✅ | ✅ | ❌ | ✅ | 部分 |
| TUIC v5 | ✅ | ✅ | ❌ | 部分 | 部分 |
| AnyTLS | ✅ | ✅ | ❌ | 部分 | 部分 |
| **Lumi(自研)** | ❌ | ❌ | ❌ | ❌ | ❌ |

写成代码常量并配测试。sing-box 需按 UA 中的版本号分支(1.11 与 1.12 的 outbound/endpoint 结构有破坏性变更)。

### 6.6 节点可见性:只由权限组决定

**这是一条产品约束,不只是实现约定。**

```
节点可见性 100% 由权限组决定,不存在任何用户级例外。
  "给单个用户开某节点" → 建一个只含该节点的组
  "隐藏节点"          → 移出所有组

实现强制:渲染入口只接受 (profile, groupIDs),
         函数签名里拿不到 userID —— 从类型上杜绝用户级过滤。
```

理由:一旦存在用户级过滤,任何按组缓存的渲染骨架都会失效,且可能让 A 用户拿到 B 用户组的节点 —— 那是越权,不是性能问题。

**例外**:节点列表中的"剩余流量/到期时间"伪节点条目**是用户级的**,必须走占位符在最后一步注入,不能进共享骨架。

### 6.7 节点数差异的用户感知

能力过滤 + Lumi 专属节点会导致 Clash 用户看到 45 个、Lumi 用户看到 50 个。用户会认为被区别对待。

```
订阅内插说明性伪节点:「ℹ️ 5 个节点需要更新客户端」(不可连接)
用户端网页显示:      「你的客户端可用 45 / 共 50 个节点」+ 升级引导
官网明确列出各客户端可用节点数
```

**把解释前置到产品里,而不是留给客服。**

### 6.8 响应头与安全

```
Subscription-Userinfo: upload=0; download=<Σ已用>; total=<Σ额度>; expire=<最晚到期>
Profile-Update-Interval: 12
Referrer-Policy: no-referrer
Cache-Control: private, no-store
```

`upload` 恒 0 是生态惯例(客户端把 up+down 相加显示),分开填会重复计数。多订阅下 `total` 取和、`expire` 取最晚(避免客户端误报已过期)。

| 安全措施 | 说明 |
|---|---|
| Token 轮换 | 一键重置,旧链接立即失效 |
| 路径可自定义 | 默认 `/s/`,避免特征扫描 |
| **访问日志掩码** | 面板对 `/s/*` 只记 token 前 6 位 —— **URL 里的 token 会进 Nginx/CDN 日志,这是订阅泄漏头号途径** |
| 频率限制 | 单 token 10/min |
| 异常告警 | 同 token 短时多地区拉取 → 风控事件(默认只记录) |
| 响应头脱敏 | 不返回框架特征头 |
| 强制 HTTPS | 订阅端点拒绝明文 |

> **v1 不做 ETag/304 订阅缓存。** 它是为已推迟的 LSF 原生格式设计的优化;而分桶 ETag 会让 `Subscription-Userinfo` 陈旧(用户看到的剩余流量停在上次 200 响应),引发无法解释的投诉。第三方订阅 6~12 小时才拉一次,不需要这个优化。

## 7. 计量核心

**这是全项目最需要工程投入的部分,也是"新世代"唯一能被量化验证的地方。** 所有既有面板的性能瓶颈都在这里,而不在 HTTP 框架。

### 7.1 问题

朴素实现(V2Board 的做法):200 节点 × 5000 用户,每 60s `for` 循环 `UPDATE users SET u=u+?`

```
= 100 万次 UPDATE / 分钟 ≈ 16,600 QPS
+ 同一用户在多节点上并发更新同一行 → 行锁竞争 → 连接池耗尽 → 502
```

这就是机场规模稍大就必须上高配机器的真实原因。

### 7.2 数据流

```
Node ──TrafficReport{seq, node_id, [{uid,up,down}]}──▶ Ingest
                                                         │
                          ┌──────────────────────────────┤
                          │ 1. seq 去重(Redis 持久化)   │
                          │ 2. 节点/用户存在性校验        │
                          │ 3. billed = (u+d)*rate_bp/100 │ ← 整数运算
                          │ 4. ACK(仅表示已入 WAL)      │
                          └──────────────┬───────────────┘
                                         ▼
                      ┌──────────────────────────────────┐
                      │  Sharded Accumulator(64 片)      │
                      │  key={uid,nid}  每片独立 mutex     │
                      └──────────────────┬───────────────┘
              ┌──────────────────────────┼──────────────────────┐
              ▼                          ▼                      ▼
     ┌────────────────┐        ┌──────────────────┐   ┌──────────────────┐
     │ Redis 热层      │        │ Quota Engine     │   │ Flusher(5s)      │
     │ HINCRBY 聚合    │───────▶│ Lua 原子判定      │   │ ①gen batch_id     │
     │ (跨订阅总量)     │        │ 超额 → 移除授权   │   │ ②WAL→Redis        │
     └────────────────┘        └──────────────────┘   │ ③Drain(map swap) │
                                                       │ ④Ladder 归属裁决  │
                                                       │ ⑤两阶段幂等落库    │
                                                       │ ⑥ACK WAL          │
                                                       └────────┬─────────┘
                                                                ▼
                                                        traffic_ledger
                                                                │ 每小时
                                                                ▼
                                            traffic_daily + subscriptions.used_bytes
                                            + 以 ledger SUM 为准回写 Redis 与 Ladder(纠偏)
```

### 7.3 Flusher 本地权威账本(Ladder)

归属需要知道"每条订阅还剩多少",三个候选来源都有问题:查库是 N+1;Redis 热层只有跨订阅总量;`subscriptions.used_bytes` 滞后一小时。

**解法:利用"Flusher 已被要求单实例"这个既有约束,让它持有内存权威账本。**

```go
type QuotaLadder struct {
    ladders map[int64][]SubQuota  // userID → 按扣费顺序排好的订阅余量
}
```

| 时机 | 行为 |
|---|---|
| 启动 | 从 `subscriptions` hydrate,再回放未 ACK 的 WAL 修正 |
| 运行 | 每次 flush 自己扣减,零 IO |
| 订阅变更 | 通过事件总线(§9)通知 Flusher 更新对应用户 |
| 每小时 | 以 `traffic_ledger` 的 SUM 为准重建,消除累积漂移 |

**代价必须说清楚**:这让 Flusher 成为**有状态单点**。它挂了,恢复期间(hydrate,预计数秒)不接受 flush,数据积压在 Accumulator 与 WAL。可接受,但必须写进架构约束 —— 否则某天有人为了扩容起两份,会直接导致**双倍扣费**。

**防呆**:Flusher 启动抢 Redis 分布式锁(带 fencing token),抢不到则只读启动并告警。不能靠部署纪律。

### 7.4 归属算法

```go
// flush 阶段执行,不在 hot path。subs 顺序固定:data_pack(到期升序) → primary
func attribute(billed int64, subs []SubQuota, at time.Time) []LedgerRow {
    var rows []LedgerRow
    remaining := billed
    for _, s := range subs {
        if s.ExpiredAt != nil && s.ExpiredAt.Before(at) { continue }
        avail := s.TransferBytes - s.UsedBytes
        if avail <= 0 { continue }
        take := min(remaining, avail)
        rows = append(rows, LedgerRow{SubscriptionID: s.ID, Billed: take})
        remaining -= take
        if remaining == 0 { break }
    }
    if remaining > 0 {
        // 全部订阅耗尽仍有剩余 = 超额溢出流量
        rows = append(rows, LedgerRow{SubscriptionID: 0, Billed: remaining})
    }
    return rows
}
```

**`sub_id = 0` 的总量是一个重要的运营指标** —— 它直接衡量"超额下线延迟"造成的损失。在仪表盘单列,目标 < 0.1%。v1 用兼容面(≤60s 延迟)时这个数会偏高,是 LNP 进 v1.1 的量化依据。

### 7.5 整数倍率

```go
// float32 尾数只有 24 位,0.3 / 1.5 在二进制里是无限循环小数,
// 不同批次舍入方向不一致 → 同样的流量分批不同算出不同结果 → 对账对不平
billed := (up + down) * int64(rateBP) / 100   // 向下取整,对用户有利
```

`(up+down)` 上限约 1e12,乘 100 后 1e14,`int64` 上限 9.2e18,无溢出。**舍入策略写进计费口径文档**。

### 7.6 两阶段幂等落库

**加法 UPSERT 不是幂等操作。** 崩溃时若"DB 已提交但 WAL 未确认",重启回放会把同一批流量再加一次 —— 这类 bug 只在崩溃后出现,平时测不出来。

```sql
BEGIN;
-- 阶段一:幂等闸门
INSERT INTO traffic_batches (batch_id) VALUES ($1) ON CONFLICT DO NOTHING;
-- 受影响行数 = 0 → 已应用过 → ROLLBACK 并 ACK WAL

-- 阶段二:仅在闸门通过时执行
INSERT INTO traffic_ledger (...)
SELECT * FROM UNNEST($2::bigint[], $3::bigint[], ...)  -- 数组传参,一次往返写数千行
ON CONFLICT (user_id, node_id, subscription_id, bucket_at) DO UPDATE
SET up_bytes     = traffic_ledger.up_bytes     + EXCLUDED.up_bytes,
    down_bytes   = traffic_ledger.down_bytes   + EXCLUDED.down_bytes,
    billed_bytes = traffic_ledger.billed_bytes + EXCLUDED.billed_bytes;
COMMIT;
```

`traffic_batches` 保留 7 天(远大于任何崩溃恢复窗口)。

**效果**

| | 朴素实现 | 本设计 |
|---|---|---|
| DB 写频率 | 16,600 QPS | **0.2 批/秒** |
| 单批行数 | 1 | 数千(合并去重后) |
| 行锁竞争 | 严重 | 无 |
| `users` 表写入 | 每次 | 每小时 rollup |

### 7.7 两种幂等,防的不是同一件事

| 机制 | 防什么 | 存储 |
|---|---|---|
| `seq` | **节点侧重传**(面板已处理但响应丢失,节点重发) | Redis,与 ingest 同 pipeline |
| `batch_id` | **面板侧重放**(WAL 崩溃恢复) | PostgreSQL `traffic_batches` |

**两个都必须有。** 只做其一必漏。Redis 全丢时退化为"可能重复计一个上报窗口",在 `doctor` 中告警。

### 7.8 严格顺序与失败处理

```
1. 生成 batch_id
2. WAL:写 Redis LIST(含 batch_id 与全部条目)
3. Drain(map 交换,锁持有时间常数级)
4. flush 到 PG(两阶段)
5. 成功 → 删 WAL;失败 → 指数退避重试
   重试超 N 次 → merge 回 Accumulator 并告警
```

**SLA 明确写进文档**:进程被 `SIGKILL` 时最多丢失 WAL 间隔内的数据(默认 5s)。`SIGTERM` 正常停机则**一条不丢**(§13.3)。

### 7.9 配额判定与重置

**原则:配额判定读 Redis,永不读 DB。**

```
user:q:{uid}                HASH   跨订阅聚合 {used, total, status}
user:q:{uid}:{sub}:{epoch}  HASH   逐订阅,重置即换 key
user:online:{uid}           SET    成员=IP 或设备指纹,TTL 90s
group:users:{gid}           SET    授权用户
node:seq:{mid}:{nid}        STRING 幂等游标
```

**重置代次(epoch)**:防止在途 flush 错算。重置时 `reset_epoch + 1`;flush 时按 `bucket_at` 与 `last_reset_at` 比较,早于重置时刻的写 ledger(历史账保留)但**不计入当前周期**。

**所有重置执行时间向下取整到 5 分钟 bucket 边界** —— 否则 `monthly_signup` 策略下重置时刻是任意时分秒,一个 bucket 会横跨重置点,里面的流量无法二分。误差最多 5 分钟,换来周期归属的确定性。

**到期判定是计算出来的,不是 cron 写出来的**:

```sql
WHERE status = 'active'
  AND (expired_at IS NULL OR expired_at > now())
  AND used_bytes < transfer_bytes
```

`status` 只是性能缓存与运营展示。**即使 cron 挂了,授权判定依然正确。**

### 7.10 设备/IP 限制

```
节点 alive 上报 → SADD user:online:{uid} <fingerprint> + EXPIRE 90s
判定:SCARD > device_limit → 移除授权
```

v1 用 IP 维度(同 NAT 下会误判,阈值应默认放宽,后台明确区分口径)。设备指纹随 Lumi 原生链路进 v1.1。

### 7.11 ★ 不变量校验器

**这是整份文档里最重要的单个组件。** 前面所有设计都在**降低出错概率**,只有这一个能让你**发现自己出错了**。

在计费系统里后者更重要:一个你不知道的错误会累积几个月,等用户发现时已无法追溯,只能全额赔付换信任。

**每小时运行:**

```
I1  Σ traffic_ledger.billed(按 sub)      == subscriptions.used_bytes
I2  Σ subscriptions.used_bytes(按 user)  == Redis 聚合计数
I3  Flusher 内存 Ladder                   == DB 计算余量
I4  Σ orders.amount(completed)           == Σ payments.amount(success)
I5  Σ balance_logs.delta(按 user)        == users.balance
I6  Σ 佣金(available+withdrawn) − 追回    == 预期佣金池
I7  traffic_batches 无"已登记但 ledger 无对应行"的孤儿批次
I8  每个 active 订阅 used_bytes <= transfer_bytes(超出说明下线延迟异常)
```

任何一条不成立 → 差异明细 + 告警 + **管理端首页红色横幅**。

配套 `lumipanel reconcile --fix --dry-run`。

**必须在 M1 与计量核心同期完成,不是上线前补。** 它是开发期间发现计量 bug 的主要手段 —— 没有它,前面所有修正是否真的生效,你无从得知。

### 7.12 压测验收(写进 CI)

```

通过标准:
  常驻内存 < 512 MB
  PostgreSQL 平均写 QPS < 20
  p99 上报处理延迟 < 50 ms
  连续 24h 无内存增长趋势
```

## 8. 业务子系统

### 8.1 认证

- 密码:**argon2id**(`t=3, m=64MB, p=4`),不用 bcrypt
- 会话:JWT access(15min)+ 不透明 refresh(存 Redis,可吊销)。**不用长期 JWT** —— 无法吊销正是 V2Board 系的问题
- refresh 轮换 + **10 秒宽限期**(吸收网络抖动)+ token family 追踪,真正的重放才吊销整族
- 防爆破:IP + 账号双维度滑动窗口 + 指数退避 + Turnstile
- **防用户枚举**:用户不存在时也执行一次对固定假哈希的 argon2;登录失败统一错误码;注册/找回一律返回"若该邮箱存在,我们已发送邮件"
- 密码重置 token:单次使用、TTL 15min、绑定当前密码哈希摘要(改密即失效)、使用后**吊销该用户全部 refresh token**

### 8.2 订单状态机

```
pending ──支付成功──▶ paid ──开通──▶ completed ──退款──▶ refunded
   │                    │
   │                    └──开通失败──▶ provisioning_failed
   │                                      ├─ 自动重试(指数退避,5 次约 30min)
   │                                      ├─ 仍失败 → 告警 + 通知用户"已收到付款,处理中"
   └──超时/取消──▶ cancelled                └─ 人工:手动开通 / 全额退款
```

开通逻辑**必须幂等**(以 order_id 为键),否则重试会重复发放额度。

### 8.3 支付

```go
type PaymentProvider interface {
    ID() string
    ConfigSchema() []ConfigField          // 后台自动渲染表单
    CreatePayment(ctx, *Order) (*PayResult, error)
    VerifyCallback(ctx, *http.Request) (*CallbackResult, error)
}
```

v1 内置:**易支付(Epay)** + **余额**。v1.1:USDT 自托管(EPUSDT/BEpusdt)、Stripe、PayPal、卡密。第三方通道走通用 Epay 协议接入,这是国内事实标准。

**回调安全(逐条落实)**

1. 验签失败**直接 404**,不回显原因
2. 幂等:`UNIQUE (provider, trade_no)`
3. **金额严格相等校验**
4. 状态机:只允许 `pending → paid`
5. 异步:回调只落库 + 入队,发货走 asynq
6. 主动查单兜底:`pending` 超 N 分钟主动查询,防回调丢失

**同一订单收到两笔不同支付**(用户双开支付页 / 换通道各付一次):幂等键只防同一笔的重复回调,防不了这个。

```sql
BEGIN;
SELECT status FROM orders WHERE id = $1 FOR UPDATE;   -- 行锁
-- status != 'pending' → 本笔为"多余支付" → 不再开通
--   → 自动入账为余额 + 生成 refundable 记录 + 通知运营者
UPDATE orders SET status='paid' WHERE id=$1 AND status='pending';  -- 二次保险
COMMIT;
```

### 8.4 套餐变更

四种语义,运营者在套餐上配置 `change_policy`:

| 模式 | 到期 | 流量 | 差价 |
|---|---|---|---|
| `reset` | 从变更日重算 | 归零为新额度 | 全额 |
| `prorate` | 保持原到期日 | 按剩余天数折算 | 新日单价×剩余天数 − 旧套餐剩余价值 |
| `stack` | 原到期 + 新周期 | 累加 | 全额 |
| `deny` | — | — | 只允许到期后变更 |

**边界**:降级时差价为负 → **入余额而非退款**(避免套现);`prorate` 用**整数天**按运营时区日界计算,不用秒;全部写审计日志附计算明细。

### 8.5 并发控制总表

**能用数据库约束表达的不变量,一律加约束。**

| 场景 | 竞态 | 机制 |
|---|---|---|
| 优惠券核销 | 超发 | `UPDATE ... WHERE used_count < limit RETURNING` + `UNIQUE(coupon_id, order_id)` |
| 套餐库存 | 超卖 | `UPDATE ... WHERE stock > 0 RETURNING` |
| 订单状态转移 | 重复开通 | `SELECT FOR UPDATE` + `WHERE status='pending'` |
| 余额扣减 | 透支 | `WHERE balance >= amount RETURNING` |
| 佣金提现 | 重复提现 | 状态机 + 行锁 + 冻结期 |
| 流量落库 | 重复计费 | `batch_id` 幂等闸门 |
| 节点上报 | 重传 | Redis `seq` |
| 配额判定 | 竞态放行 | Redis Lua 原子脚本 |
| 定时任务 | 多副本重复 | Redis 锁 + fencing token,**每任务独立锁** |

### 8.6 邀请返佣(资损风险最高的模块)

```
pending ──(订单完成 + T 天冻结期)──▶ available ──▶ withdrawing ──▶ withdrawn
   └──(冻结期内退款)──▶ voided                                     [无损失]

冻结期后退款:
  → 从邀请人 available 扣回
  → 不足 → negative_balance,冻结提现直至补平
  → 标记该邀请关系为 risk,人工复核
```

`T` 默认 7 天,**应大于支付通道的争议期**。退款按钮显示"将追回 ¥X 佣金"预览。

**自我邀请与循环**:注册校验 `invite_user_id != self`;沿链上溯最多 10 层做环检测;同 IP/同设备批量注册标记 `suspect`,佣金默认不结算需人工放行。

> 佣金模块建议放在 v1.1 —— 它资损面最大,应在核心稳定后再做。

### 8.7 计费时区

全局配置 `billing_timezone`(默认 `Asia/Shanghai`)。所有周期边界(重置、到期、日报表)按该时区**当地零点**计算。存储仍 UTC,只在算边界时转换。

**这条必须写进计费口径文档并在后台显示** —— 否则 UTC 面板服务 UTC+8 用户时,重置发生在当地早上 8 点,用户会以为流量被吞。

### 8.8 通知

统一 `Notifier` 接口:邮件(SMTP 多组轮换)、Telegram Bot、Webhook、站内信。

**所有通知走 asynq 队列 + 重试**,绝不在请求线程内同步发信。

**退信与投诉处理**(缺了会让发信域名进黑名单,注册流程直接瘫痪):硬退信立即加入 `email_suppressions` 并标记用户;软退信重试 3 次后抑制;投诉率超阈值自动切通道并告警;后台可见发信健康度。

### 8.9 v1 运营工具(竞品全部空白)

**★ 用户自助诊断 —— 本项目 ROI 最高的单个功能**

前台一个按钮,一次性检查并输出:

```
✅ 账号状态正常,套餐有效至 2026-08-15
✅ 订阅链接可正常拉取(最近一次:3 分钟前)
⚠️ 流量已用 96.2%(剩余 3.8 GB)
✅ 设备数 2 / 3
⚠️ 检测到你的客户端为 Clash for Windows(旧内核)
   → 不支持本站 12 个新协议节点,建议更换 Clash Verge Rev
✅ 你可用的 38 个节点中 37 个在线

诊断码:LP-7F3A-2026072612   ← 提交工单时附上
```

**它把客服的前三轮问答前置到产品里**,预计消化三到四成"连不上"工单。实现成本约 1 周。

**工单上下文自动附加**:工单自动携带同一份诊断快照 + 近 7 天流量曲线 + 最近客户端 UA + 最近订单。客服打开即见,与诊断复用同一份数据,边际成本约 2 天。

**节点健康探测(v1 基础版)**:入口可达性多地探测 + 异常自动从订阅摘除 + 恢复自动加回。前台显示「维护中」而**不是让节点消失** —— 节点消失 = 用户以为被减配 = 工单。

### 8.10 v1.1 运营工具

- **节点批量轮换**:节点模板 + 批量替换 IP/域名 + 灰度切换 + 一键回滚 + 到期机器提醒。把半小时手工操作压到两分钟

- **到期挽回**:7/3/1 天多档提醒 → 到期未续自动发定向券 → 7/30 天召回 → 各档转化率
- **定向内容**:公告/知识库/套餐/菜单统一支持受众条件(权限组/套餐/到期状态/注册时长)
- **风控中心**:分享检测、异常注册、薅券、退款滥用。三档处置,**默认只记录不处置** —— 误封成本远高于漏封

## 9. 前后台联动 ★

**竞品最弱的一环,也是最能拉开差距的地方。**

竞品把前台和后台当两个应用做,只共享数据库,于是"改了不生效""封了还能连""套餐改了订阅没变"反复出现,标准答案是"清一下缓存"。

**正确心智模型:前台和后台不是两个系统,是同一份状态的两个视图。**

### 9.1 类型①:配置 → 呈现

**配置版本号 + 响应头协商**

```
后端:任何影响前台呈现的配置变更 → config_version 自增
     所有 API 响应带 X-Config-Version

前端:发现响应头 version 与本地不一致
     → 失效相关 TanStack Query 缓存 → 自动重拉 → 用户无感,不刷新页面
```

比轮询整个配置便宜,比 WebSocket 简单,且不需要前端为每个配置项单独订阅。覆盖:套餐上下架、价格、公告、支付方式、主题、菜单可见性、站点文案。

### 9.2 类型②:管理动作 → 即时生效

**反面教材(竞品做法)**:handler 里依次改表、清缓存、发通知。三件事任一漏掉就产生不一致,且每新增一个管理动作都要重写一遍。

**正确做法:管理动作只发一个领域事件。**

```
管理员封禁用户
   └─▶ event: user.banned { user_id, reason, operator_id }
          ├─▶ 节点侧:从 group:users 移除授权
          ├─▶ 用户端:吊销全部会话 + 后续请求返回带原因的 403
          ├─▶ 订阅:  该 token 立即返回 403
          ├─▶ 通知:  按配置发邮件/TG
          └─▶ 审计:  记录操作者、原因、时间
```

**联动矩阵**(直接对应代码里的事件订阅注册表)

| 管理动作 | 节点侧 | 用户端 | 订阅 | 通知 | 审计 |
|---|:---:|:---:|:---:|:---:|:---:|
| 封禁/解封 | 移除授权 | 吊销会话 | 失效 | ✅ | ✅ |
| 修改套餐 | 权限组变更 | 刷新展示 | 节点集变化 | ✅ | ✅ |
| 重置流量 | 恢复授权 | 刷新展示 | — | ✅ | ✅ |
| 调整额度 | 更新 Ladder | 刷新展示 | — | 可选 | ✅ |
| 节点上下线 | 停/起 inbound | 列表变化 | 重新渲染 | 可选 | ✅ |
| 节点改倍率 | 计费倍率 | 展示更新 | 名称标注 | ❌ | ✅ |
| 套餐上下架 | — | 商店隐藏 | — | ❌ | ✅ |
| 手动开通 | 授权生效 | 订单状态 | 生效 | ✅ | ✅ |
| 退款 | 撤销授权 | 余额/状态 | 失效 | ✅ | ✅ |
| 重置订阅 token | — | 新链接 | 旧链接失效 | ✅ | ✅ |
| 发布公告 | — | 站内展示 | 可选伪节点 | 按受众 | ✅ |

### 9.3 三条实现约束

```
1. 领域事件是唯一的副作用入口
   handler 只做"校验 + 改主状态 + 发事件",
   禁止在 handler 里直接调通知、清缓存、推节点。

2. 订阅者必须幂等且失败隔离
   通知发送失败不能回滚封禁操作。各自入队重试,互不影响。

3. 每个事件配一个联动测试
   断言:发出事件后,矩阵中该行的所有副作用都发生了。
   这是防止"新增功能漏掉某一路"的唯一可靠手段。
```

**事件总线是架构决策,不是功能,不可推迟到 v1.1。** 若 v1 用"handler 里依次调用"的写法,后面每个管理动作都要重写,且必然遗留不一致 bug。

### 9.4 类型③:用户行为 → 后台可见(反向联动)

竞品几乎没有这一类,但它把**用户侧真实状况变成运营决策的输入**。

**★ 未识别客户端统计**

每次订阅请求 UA 未命中已知规则就记一条 `unknown_clients`。后台按用户数排序展示:

```
最近 30 天未识别客户端 TOP
  1. Egern/2.x     412 次   87 个用户
  2. Loon/3.x      203 次   51 个用户
  3. <空 UA>       156 次   —
```

**它把"客服承接长尾"这条模糊策略变成有数据依据的工程决策** —— 某客户端用户数越过阈值就该给它写渲染器,不用拍脑袋也不用等客服抱怨。

**客服负担门禁**:按工单类型分类统计,任一类型月度工单数 > 用户数 × 2% → 触发工程侧复盘。**该问题应当被产品修掉,而不是继续人力承接。** 客服组不可水平扩展,成本随用户数线性增长。

**支付漏斗**:浏览套餐 → 下单 → 发起支付 → 支付成功 → 开通成功,各步转化率与失败原因。直接暴露通道问题。

### 9.5 类型④:系统事件 → 双向呈现

```
节点探测失败
   └─▶ event: node.unhealthy
          ├─▶ 后台:告警 + 标红 + 自动从订阅摘除
          ├─▶ 前台:显示「维护中」(不是消失)
          └─▶ 可选:超阈值时自动发布公告
```

同样适用于:支付通道异常(前台自动隐藏该通道并提示改用其他)、计划维护(前台横幅)、不变量告警(仅后台)。

## 10. 前端设计

### 10.1 工程结构

```
web/
├── packages/{api, ui, shared}     # api 由 OpenAPI 生成,禁止手写
└── apps/{landing, user, admin}
构建:pnpm workspace + Vite → web/dist → Go //go:embed → 单二进制
```

**类型贯通链**:Go handler → OpenAPI → `openapi-typescript` → 前端。**CI 校验生成物与提交物一致**,否则类型漂移会在运行时才暴露 —— 那正是选 Go 想避免的问题,前端这段不能断链。

**int64 用 string 传输。** JS `Number` 是 float64,安全整数上限约 9.007e15;流量字节数在 PB 级会失真。OpenAPI 标 `format: int64` 生成 `string`,前端用 `BigInt`。**这是真实会在大机场触发的 bug。**

### 10.2 数据层

| 关注点 | 选型 | 理由 |
|---|---|---|
| 服务端状态 | TanStack Query | 缓存/失效/重试/轮询一体;配合 §9.1 的版本协商 |
| 客户端状态 | Zustand | 只用于会话、主题、侧栏 |
| 表单 | React Hook Form + Zod | schema 可从 OpenAPI 生成,与后端校验同源 |
| 图表 | ECharts | 30 天 × 5min 数据点多,canvas + dataZoom 优于 SVG |
| 表格 | TanStack Table + Virtual | 超过 200 行强制虚拟滚动 |

**不用 Redux** —— 服务端状态占 95%,引入只会制造两套状态源。

**轮询在页面不可见时必须暂停**(`refetchIntervalInBackground: false`)。

### 10.3 认证(两个 S1 修正)

```
access token   → 仅存内存(模块变量/Zustand,不持久化),TTL 15min
refresh token  → httpOnly + Secure + SameSite=Strict Cookie
                 Path=/api/v1/auth/refresh(作用域最小化),TTL 30 天,每次轮换
```

**绝不使用 localStorage / sessionStorage 存任何凭据。** 这是 V2Board 系的通病 —— 一个存储型 XSS 就能批量导出所有登录用户的 token。内存存储在 XSS 下仍可被读,但**不可持久化窃取**,风险面小一个数量级。

代价:刷新页面需静默 refresh 一次。首屏加 `bootstrap` 状态显示骨架屏,否则用户每次刷新都会看到一闪而过的登录页。

**★ single-flight refresh**

页面同时发 5 个请求 → 都收到 401 → 各自触发 refresh → 第一个成功并轮换作废旧 token → 后 4 个被判定为**重放攻击** → 吊销整个会话族 → **用户被强制登出**。这个 bug 在开发环境几乎测不出来(请求少、网络快),上线后表现为"用户随机掉线"。

```ts
let refreshInflight: Promise<string> | null = null;
async function getFreshToken() {
  if (refreshInflight) return refreshInflight;          // 复用 in-flight promise
  refreshInflight = fetch('/api/v1/auth/refresh', {method:'POST', credentials:'include'})
    .then(async r => { if (!r.ok) throw new SessionExpired();
                       const {access_token} = await r.json();
                       setAccessToken(access_token); return access_token; })
    .finally(() => { refreshInflight = null; });
  return refreshInflight;
}
// 拦截器:401 → 等待单飞 → 重放原请求(每请求只重试一次,防死循环)
```

**全局登出必须清 TanStack Query 缓存** —— 否则残留数据会串号。

### 10.4 随机管理路径与 SPA fallback

后端服务 `index.html` 时**注入**基础路径:

```html
<meta name="app-base" content="/a7f3k9x2/">
```

Vite 设 `base: './'`,`<BrowserRouter basename={base}>`。**部署测试用例:换一次 secure path,验证管理端仍能加载。**

**路由优先级(顺序不可颠倒)**

```
1. /api/**              → API;未匹配返回 JSON 404
2. /s/**                → 订阅
3. /{secure}/assets/**  → 静态文件;不存在返回 404(★ 绝不 fallback)
4. /{secure}/**         → admin index.html
5. /app/assets/**       → 静态文件;不存在返回 404
6. /app/**              → user index.html
7. /                    → landing
```

**第 3、5 条是关键**:若对缺失的 `.js` 也返回 `index.html`,浏览器拿到 `Content-Type: text/html` 的脚本,报 `Unexpected token '<'` —— 这个报错完全指不到真正原因(通常是缓存了旧 index.html 引用已删除的 hash 文件),会浪费大量排查时间。

`index.html` 设 `no-cache`,hash 资源设 `immutable, max-age=31536000`。

### 10.5 设计语言

**产品性质:仪表盘/控制台,不是营销页。** 运营者每天在管理端待数小时;终端用户主要在手机上快速查"还剩多少流量、什么时候到期"。设计职责是**让数值可读、让状态一眼可辨**。

**主题:网络设备仪表(instrument panel)** —— 灵感取自题材本身的器物:设备状态面板、链路指示灯、监控终端。所有决策从这里推导,不从通用后台模板推导。

**Typography**

| 角色 | 字体 | 用途 |
|---|---|---|
| UI/正文 | IBM Plex Sans + IBM Plex Sans SC | 界面与中文正文 |
| 数据 | IBM Plex Mono(启用 `tnum`) | **所有数值**:流量、金额、端口、RTT、UUID、时间戳、订单号 |

选 Plex 而非 Inter 的理由:它为技术语境设计,Sans/Mono 同族、基线与字重完全咬合;且有完整简中子族 —— 在以中文为主的场景这是硬需求(Inter 无中文,混排必然要另配一套,字重与字面会打架)。

**规则:凡"可以被测量的东西",一律 Mono + tabular figures,包括正文中夹带的数字。** 这是本设计唯一刻意越界的地方 —— 一般后台不这么做,但对一个每个数字都是测量值的产品,这是正确的。

**Palette**

```
--ink        #101720   近海军蓝而非纯黑,长时间阅读更柔和
--ink-muted  #5B6774
--paper      #F4F6F8
--surface    #FFFFFF
--line       #DCE1E7   发丝级 1px

--link       #1F6FEB   活跃/在线/可点击
--flow       #0E9F6E   流量与增长
--warn       #B45309   接近额度/即将到期
--halt       #B42318   离线/封禁/已过期
--idle       #98A2B3   停用/无数据

暗色:--paper #0B0F14,--surface #131A22,同色相高明度变体
```

依据是**状态语义**:蓝=通,绿=流,琥珀=将尽,红=断。运营者看一眼颜色就知道该处理什么,颜色不是装饰。

**Signature:链路状态条** —— 每个节点在管理端表格、用户端列表、Lumi 客户端渲染同一个构件:

```
HK-01  ●  38ms  0.0%  ▁▂▃▅▂▁▂  ×1.0
       状态 RTT  丢包   1h负载    倍率
```

全部 Mono,像网络设备的一行状态输出。它是全产品的记忆点与三端视觉一致性的锚。

**Motion**:只保留数值滚动过渡(200ms)与状态色淡入(150ms),全部包 `prefers-reduced-motion`。仪表产品的动效多一分就显得不可信。

### 10.6 文案

- **按用户能控制的东西命名**:是"流量与到期",不是"配额实体"
- **动作词全流程一致**:按钮"保存修改" → 提示"已保存",不能变成"提交成功"
- **错误说清发生了什么 + 怎么办**,不道歉不含糊
  - ✗「操作失败,请重试」
  - ✓「优惠券已达使用上限。换一张或直接下单。」
- **空状态是行动邀请**:✓「还没有节点。添加第一台机器后,节点会自动出现在这里。」
- 中文排版:数字与中文间加空格;金额/流量/时间统一格式化函数,禁止各页面自拼

### 10.7 可访问性与移动端

- `:focus-visible` 明确描边,不要 `outline: none`
- 颜色不是唯一信息载体:状态点旁必须有文字或图标
- 对比度 ≥ 4.5:1(正文)/ 3:1(大字与图形)
- 用户端**移动优先**:剩余流量、到期日、复制订阅按钮必须首屏无滚动可见
- 管理端最小支持平板;手机提供只读关键指标视图
- 复制订阅:`navigator.clipboard` + 降级路径(非 HTTPS 下不可用),复制后明确反馈

### 10.8 前端易错点清单

| # | 陷阱 | 对策 |
|---|---|---|
| 1 | 大整数用 JS `number` | int64 走 string + BigInt |
| 2 | 金额浮点计算 | 全程整数,只在显示时格式化 |
| 3 | 时区显示与计费时区不一致 | 显示到期时标注时区,与 `billing_timezone` 对齐 |
| 4 | 表格未虚拟化 | >200 行强制 |
| 5 | 轮询不暂停 | 页面不可见时停止 |
| 6 | 登出未清查询缓存 | 串号事故 |
| 7 | 动态表单硬编码字段 | 由后端 `ConfigSchema` 驱动 |
| 8 | password 字段回显覆盖密钥 | 回显掩码占位符,值未变则不覆盖 —— **非常常见的实现 bug** |
| 9 | i18n 拼接句子 | 用带占位符的完整句模板 |
| 10 | 危险操作无二次确认 | 删除/退款/批量需输入名称确认 |
| 11 | 前端无错误上报 | 接错误监控,后端有 observability 前端不能没有 |

## 11. 扩展性

Go 没有 PHP 那样廉价的动态插件。**三层策略,按扩展需求性质分流:**

| 层 | 机制 | 适用 | 需重编译 |
|---|---|---|---|
| L1 内建注册 | `init()` + build tag | 支付、通知、渲染器、认证方式 | 是 |
| L2 WASM | wazero 加载 `.wasm` | 风控规则、自定义计费、订阅后处理 | 否 |
| L3 Webhook | 出站 HTTP + 声明式配置 | 与外部系统集成 | 否 |

**判断**:90% 的第三方需求("接一个新支付通道""下单时通知我的系统")用 L3 就够,而 L3 零风险零耦合。L2 只对确需低延迟内联执行的场景开放,WASM 沙箱本身提供隔离(比 PHP 插件能 `eval` 任意代码安全得多)。L1 保留给核心。

**事件总线即 L3 基础**(与 §9 同一套):管理员配置 事件类型 → 目标 URL → 密钥 → 重试策略,出站走队列,可查投递日志。

**主题**:CSS 变量 + 布局槽位换肤;深度定制走"外置前端"模式 —— 面板只提供 OpenAPI,运营者可自己写前端。

## 12. 安全设计

### 12.1 认证凭据带外原则

**铁律:任何可用于认证的凭据(魔法链接、验证码、重置 token、API key 明文),只允许通过带外通道送达,绝不出现在任何 API 响应体中。**

用类型系统强制,而不是靠 code review:

```go
type Secret struct{ v string }
func (s Secret) Reveal() string { return s.v }          // 仅带外发送器可调用
func (s Secret) String() string { return "[REDACTED]" } // 日志安全
func (s Secret) MarshalJSON() ([]byte, error) {
    return nil, errors.New("security: Secret must never be serialized into a response")
}
```

**三道防线**

1. **CI 静态检查(主防线)**:禁止 `Reveal()` 出现在 `internal/api/**` 与 `internal/subplane/**`
2. **契约测试**:所有认证端点断言响应体不匹配 token 模式正则
3. **运行时兜底**:统一响应写入器先 Marshal 到缓冲区,成功才写 header 与 body;失败记 `CRITICAL` 并返回干净 500。**永远不流式序列化响应体** —— 否则会输出半截 JSON

魔法链接功能**默认关闭**,开启时后台显示安全提示。

### 12.2 密钥加密存储

配置全部入库是对的,但支付密钥、SMTP 密码、Bot Token 若明文存储,一次 SQL 注入或备份泄漏就等于资金账户失守 —— 而机场类项目的数据库备份经常被随手扔在服务器上。

```
主密钥:  环境变量 LUMI_MASTER_KEY(32 字节),绝不入库、绝不进配置文件
字段加密:settings 中标记为 secret 的行用 AES-256-GCM,
         每行独立 nonce,AAD 绑定 setting key(防密文换位)
内存:    解密后包装为 Secret 类型
轮换:    lumipanel rotate-key --old --new
备份:    逻辑备份中的密文无主密钥不可用 —— 这才是加密的意义
启动:    主密钥缺失时拒绝启动并明确提示,不降级成明文
```

### 12.3 权限

RBAC 三角色:`user` / `staff`(只读+工单)/ `admin`。

- 权限检查是**中间件强制路径**。默认拒绝:新增路由未显式声明所需权限,**启动时 panic**
- 越权返回统一 403,不泄漏资源是否存在
- 管理后台路径随机 + 可选 IP 白名单 + 可选强制 2FA

**模拟登录会话必须收窄**(否则内部人员可改密码夺走账号、用余额下单):

```
JWT 带 impersonated_by 声明;中间件强制拒绝:
  改密码/邮箱/2FA · 提现/余额支付/下单 · 重置订阅 token · 任何管理端接口
UI 持续显示醒目横幅;TTL 强制 30 分钟;
用户侧"登录记录"中可见该次模拟(谁、何时、多久)
```

### 12.4 输入输出

- 所有入参绑定显式 request struct + validator,**拒绝 `map[string]any` 直通**
- 所有 SQL 走 sqlc 参数化,禁止拼接(CI 静态检查)
- 排序/筛选字段走白名单枚举
- 错误码枚举化,生产**绝不回显堆栈或 SQL**

### 12.5 限流

| 类别 | 维度 | 默认 |
|---|---|---|
| 认证 | IP + 账号 | 5/min,失败指数退避 |
| 发信 | 账号 | 1/60s,10/day |
| 订阅拉取 | token | 10/min |
| 普通读 | 用户 | 120/min |
| 写操作 | 用户 | 30/min |
| 支付回调 | 通道 IP 白名单 | 不限流但记录 |
| 开放 API | API Key | 按 key 配置 |

Redis 滑动窗口;超限返回 429 + `Retry-After`;**限流命中率作为监控指标**(突增即攻击信号)。

### 12.6 抗审查与去特征化

订阅路径可配置 + token 可轮换 + 自定义域名;后台路径安装时随机生成、可随时更换;移除框架特征头、错误页可自定义、404 行为与普通静态站一致;支持自动 ACME、建议前置 CDN;落地页可配置成完全无关的静态页;订阅响应不泄漏节点内网/真实 IP。

### 12.7 审计与用户删除

`audit_logs` 记录:操作者、IP、UA、动作、目标、变更前后 diff、时间。覆盖所有管理端写操作、配置变更、模拟登录、提现审核、退款。**只追加不可改。**

`settings_history` 记录配置变更并支持回滚;关键配置(支付、通讯密钥、计费口径)变更需二次确认并填写原因。

**用户删除 = 匿名化,不是物理删除。** `traffic_ledger` 引用 user_id 且必须保留(财务凭证),级联删除会破坏账目。清空邮箱/密码/备注,置 `deleted_at`,保留 id 与账目;订阅终止;token 立即失效。`lumipanel purge --before` 在保留期后彻底清理。

## 13. 可观测性与运维

### 13.1 观测

| 维度 | 方案 |
|---|---|
| 指标 | Prometheus `/metrics`(默认绑内网)。核心:上报处理延迟、flush 批量大小、连接池、在线节点数、订阅 QPS、支付成功率、**不变量校验结果**、`sub_id=0` 溢出占比 |
| 日志 | `log/slog` 结构化 JSON,request_id 贯穿;`/s/*` 路径掩码 |
| 追踪 | OpenTelemetry,可选 |
| 健康 | `/healthz`(存活)、`/readyz`(DB+Redis 就绪) |
| 前端 | 错误监控上报(不能只有后端有 observability) |

### 13.2 自检

`lumipanel doctor`:DB/Redis 连通(**Redis 不可达为致命错误**)、时钟偏差、磁盘余量、证书有效期、分区表状态、队列积压、主密钥存在性、Flusher 锁状态。

### 13.3 优雅停机

`SIGKILL` 最多丢 5s 是可接受的,但正常升级用 `SIGTERM`,应该**一条都不丢**。

```
1. /readyz 立即 503(负载均衡摘流量)
2. 停止接受新连接,等待在途请求(上限 15s)
3. 停止 Accumulator 接收
4. ★ 强制 flush 全部分片,等待落库确认
5. 释放 Flusher 分布式锁
6. 关闭连接池 → 退出
总超时 60s;超时则记 CRITICAL 后强退(WAL 保证可恢复)
```

**Kubernetes 需配 `terminationGracePeriodSeconds: 90`** —— 否则默认 30s 会在第 4 步被打断。这条必须写进部署文档。

### 13.4 备份与升级

`lumipanel backup` 导出逻辑备份(业务数据 + `traffic_daily`,不含流量明细);二进制替换 + `migrate up`;迁移必须可回滚;升级前自动备份。

**备份可恢复要真做一次恢复演练,不能只验证导出成功。**

## 14. 迁移方案

独立子命令,**只读源库,绝不写回**:

```bash
lumipanel import xboard  --dsn="mysql://..." --dry-run        # v1
lumipanel import v2board --dsn="mysql://..." --version=1.7.4  # v1.1
lumipanel import xiaov2b --dsn="mysql://..."                  # v1.1
lumipanel import ppanel  --dsn="mysql://..."                  # v1.1
lumipanel import v3board --dsn="postgres://..."               # v1.1
```

**必须保证的不变量**

1. **订阅 token 保留** —— 用户不需要重新导入订阅链接,这是"零感知"的关键
2. **UUID 保留** —— 节点侧用户标识不变
3. **到期时间与剩余流量精确保留**,误差为零
4. 历史流量明细**不迁移**(体量大价值低),只迁日粒度汇总
5. 密码哈希:V2Board 用 bcrypt/md5 混合,导入后保留原哈希并标记,用户下次登录成功时**透明升级为 argon2id**
6. 单套餐 → 一条 `primary` 订阅
7. `--dry-run` 必须输出完整差异报告:将导入多少用户/订单/节点,哪些字段无法映射,哪些数据会被丢弃

| 源 | 主要差异 | 策略 |
|---|---|---|
| Xboard | 配置已入库;节点表有改动;有插件数据 | 配置可直接映射;插件数据不迁移,生成报告 |
| V2Board 1.7.x | 套餐挂 users 表;配置在 PHP 文件 | 每用户生成一条 subscription;配置需单独 `import config` |
| xiaoV2b | V2Board + 分支特有字段 | 复用 V2Board 导入器 + 补丁 |
| PPanel / V3Board | 独立 schema | 各自独立导入器 |

## 16. LumiNode(V2bX 扩展分支)

### 16.1 定位修正:是"扩展",不是"魔改"

V2bX 的配置里 `Cores` 是一个**数组**,可以同时运行 `sing`、`xray`、`hysteria2` 等多个内核实例,各有独立配置,并通过 build tag 选择编译哪些。

**含义:不需要魔改,只需要增加一个 core。现有内核代码一行都不用碰。**

```
Cores: [ {Type:"xray",...}, {Type:"sing",...}, {Type:"lumi",...} ]
                                                  └── 新增,build tag 控制
```

### 16.2 Fork 纪律 —— 最大的长期风险

上游会持续跟进 xray-core / sing-box 的版本、新协议、安全修复。分叉越深,合并成本越高,直到某天放弃跟进 —— 然后节点端就停在了某个协议已不再能穿透的版本上。**V2Board 生态里多数 fork 就是这样死的。**

| 模式 | 上游合并成本 | 采用 |
|---|---|---|
| A 深度改造(散布修改) | 极高,几次后放弃 | ❌ |
| **B 加法扩展**(只增文件) | 低,基本无冲突 | ✅ |
| C 外挂进程 | 零 | 备选,但流量统计与生命周期要重做 |

**模式 B 硬规则**

```
1. 禁止修改任何已有文件,除两处白名单:
     core/registry.go(注册新 core,单行) · go.mod
2. 新代码全部在 core/lumi/ 与 protocol/lumi/ 下
3. build tag 隔离://go:build lumi
   不带该 tag 编译时,产物行为与上游二进制完全一致
4. 每月固定 git merge upstream,CI 自动跑
   冲突数 > 0 即视为纪律被破坏,立即修正而不是硬合
5. 保留不含 lumi tag 的 CI 构建目标,持续证明未污染上游路径

验收:任何时候都能在 30 分钟内合入上游最新版本。
```

**供应链**:订阅上游 release/security advisory;`govulncheck` 进 CI 每周跑;维护"上游版本 ↔ fork 版本"对照表,发版时标注基线。

### 16.3 Lumi 协议插入点

**推荐:注册为 sing-box 的一个 inbound,但用适配层隔离。**

理由:代理服务端真正的工作量不在收发包,而在路由、DNS 分流、出站策略、连接复用、优雅重载 —— sing-box 这些都已做好且大规模验证。自己实现是几个月的工作,还会重踩一遍坑。

风险控制:在 `protocol/lumi/` 定义自己的接口,再写一层薄适配对接 sing-box。上游接口变化时只改适配层。

**服务端与客户端共用一份实现**

```
lumi-protocol/transport/
├── protocol.go   握手、帧格式、状态机 —— 纯逻辑,无 IO
├── server.go     LumiNode 用(sing-box inbound)
└── client.go     Lumi App 用(sing-box outbound)
```

协议逻辑写一次,两端各包一层适配。这消除了同类项目最常见的一类 bug:两端各自实现,理解出现细微偏差,表现为"偶发连接失败"。

### 16.4 协议安全:写第一行代码之前必须回答的问题

**Lumi 协议解决的是什么问题?** 如果答案是"更好的抗封锁",那这是**密码学与流量分析**问题,不是工程问题。

- 针对"全加密流量"本身的被动检测早已部署 —— 一段流量若看起来像随机加密字节、不像任何正常协议,反而会成为被盯上的特征
- 自研协议若未经流量指纹分析,极可能引入比现有协议**更明显**的特征
- Reality / Hysteria2 / AnyTLS 背后是多年对抗迭代

**四条建议**

1. 不要为了"有自研协议"而做自研协议。先明确它相对现有方案的具体改进点,并设计**可测量的**验证方法
2. **不自造密码学原语**。握手用 TLS 1.3 或 Noise Framework,自研部分限于传输层封装与流量整形
3. 上线前做主动探测测试与流量指纹对比(与真实 HTTPS 流量做统计特征比对)
4. **保留随时关闭自研协议的能力** —— 把它设计成可开关的增量,而不是架构基石

这与"自研协议不一定使用"的定位完全一致。**它不在 v1 关键路径上。**

### 16.5 双监听

自研协议对所有第三方客户端不可见,因此同机双监听:

```
机器 hk-01
  ├── 节点 A: VLESS+Reality :443   visible_to = all
  └── 节点 B: Lumi          :8443  visible_to = lumi_only
```

**运营注意**:同一物理线路出现两个节点条目,用户会问区别。UI 应合并展示为一个节点的两种接入方式。

| 数据模型 | 85% | ✅(orders/payments/tickets 等表未给 DDL) |
| 前端 | 80% | ✅(i18n 与错误监控选型未定) |
| 业务/支付 | 80% | ⚠️ 易支付对接细节需实现时确认 |
| 迁移 | 70% | ⚠️ 需真实 dump 验证 |
| 运维 | 70% | ⚠️ 安装向导未设计(D-53) |
| **中转链路** | **20%** | ❌ **阻塞** |
| **LumiNode 分发升级** | **10%** | ❌ 阻塞 v1 发布,不阻塞开发启动 |
| 邮件模板 / i18n | 30% | ❌ 阻塞 M7 |

## D.2 结论

**这份文档已经足够交付开发,但按它写完仍然不能直接投产。** 两句话是不同的判断,不要混为一谈。

**可以立刻开工的部分**:M0~M4 的设计完备度足以让开发者直接动手,不需要边写边猜。
**必须先补的**:**中转链路(C-1)会改 schema,必须在 M0 结束前拍板**,否则 M1 之后返工代价极高。

**为什么"写完≠可投产"** —— 三类差距性质完全不同:

| 类别 | 能否靠设计消除 | 现状 |
|---|---|---|
| **设计缺口** | ✅ 可以 | 七轮共 66 项,已收敛(第七轮只找到 9 项,其中 4 项是"从未设计"而非"设计错误")。**边际收益已明显递减,继续评审不如开工** |
| **工程质量** | ⚠️ 靠可验证门禁 | §15 的清单必须全部自动化。设计正确 ≠ 实现正确 |
| **运营成熟度** | ❌ **无法消除** | 支付通道会毫无预警封号、用户会用三年前的客户端版本、机房会凌晨三点重启、会有人专门研究你的漏洞。**这部分没有捷径** |

## D.3 分级投产门禁

不要问"能不能投产",要问"能投到哪一级"。

| 门禁 | 条件 | 可承载 |
|---|---|---|
| **Gate 0 · 自用** | 功能跑通;不变量校验器上线且连续 7 天无告警 | 自己 + 几个朋友,< 20 人 |
| **Gate 1 · 内测** | §15 计费 + 资金清单全绿;混沌测试通过;完整备份恢复演练过一次 | 单一真实机场 < 200 人,**运营者知情且愿担风险** |
| **Gate 2 · 公测** | §15 全部全绿;Xboard 完整迁移验证;30 天生产运行零计费差异;有回滚预案 | < 2000 人,保留旧面板可回切 |
| **Gate 3 · 通用发布** | 三家以上独立运营者各稳定 60 天;走过至少一次真实支付争议与一次节点大规模故障;文档完整 | 公开推荐他人使用 |

**Gate 1 是分水岭。** 在此之前你只是在写代码;在此之后,别人的钱和用户信任压在你的 bug 上。

## D.4 到 Gate 1 的最短路径

```
0. ★ 先拍板 C-1(中转链路)—— 它改 schema,现在做最便宜
1. M0 + M1,不变量校验器与计量核心同期完成
2. 写 fake-node,跑满压测 + 混沌测试
3. M2 兼容面,用真实 V2bX 对接
4. M3 三种渲染器
5. M4 事件总线 + 易支付 + 余额
6. 最小可用管理端(可以先做得很丑)
7. 自己真金白银用自己的面板跑 30 天 → Gate 0
8. 找一个明确知情、愿当小白鼠的运营者 → Gate 1
```

**第 7 步性价比最高。** 它会在三天内暴露出设计阶段完全没想到的东西 —— 而那正是 D.2 表格里第三类差距唯一的获取方式。

## D.5 最后

这份设计的价值不在于"完整",而在于**它知道自己哪里不完整,以及不完整会怎样**。

七轮评审收敛到附录 C 的六个待决事项和三处硬缺口,这已经比大多数开源面板起步时清晰得多。剩下的两个能力——**能证明自己是对的**(不变量校验器 + 自动化门禁)和**扛过真实世界的粗暴**(只能靠时间)——第一个现在就能建,第二个建议不要试图跳过。

**建议下一步:拍板 C-1,然后开工 M0。评审到此收敛,再审的边际收益已经低于开工的收益。**
